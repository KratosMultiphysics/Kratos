# Examples

Two collections. The **notebooks** in `applications/PhysicsNeMoApplication/examples/notebooks/` are the learning path: small analytic problems, minutes on a CPU, one concept each. The **use cases** in the [Examples repository](https://github.com/KratosMultiphysics/Examples/tree/master/physics_nemo_application) are complete workflows on real Kratos solves, each with its own README, numbered scripts and figures regenerated by the code.

## Where to start

| If you want | Start with |
|---|---|
| the whole path once, in an hour | notebook 03, then [From scratch](../General/From_Scratch.html) |
| the same on a real solver, with governance | the thermal surrogate lifecycle use case |
| unstructured meshes and graphs | notebooks 02 and 06, then the cavity and shape-optimization use cases |
| grids, superresolution, diffusion | notebooks 05, 09, 15, then the three superresolution and diffusion use cases |
| time | notebooks 08 and 16, then the transient thermo-mechanical and transient superresolution use cases |
| gradients through the solver | notebooks 17 and 19, then the adjoint integration use case |
| trust | the uncertainty-and-trust, active-learning and geometry-guardrail use cases |
| particles and molecular dynamics | notebook 20, then the Lennard-Jones use case |
| steering a trained generator without retraining | notebooks 09 and 15, then the residual-guided diffusion use case |
| operators with no reduced basis | the boundary-to-interior operators use case |
| generative design, scored by the solver | the generative topology design use case |

## Notebooks

Every notebook is committed with its outputs executed, and every one renders what it solves - the model part, the field a process wrote, the error - with pyvista through the core `KratosMultiphysics.pyvista_utilities` bridge, so the mesh and the fields are visible before any number is read. The renders are the notebook-derived figures on the topic pages.

Runnable, CPU-capable, ordered as a learning path; each states its prerequisites up front and writes to a local `./output/`. They are **executed** by `tests/test_notebooks.py` on the validation suite, one test per notebook in a throwaway copy of the tree, so a changed signature breaks a test rather than rotting silently. The notebooks marked "asserts" check a reproducible numeric claim; the unseeded ones deliberately assert nothing beyond running.
